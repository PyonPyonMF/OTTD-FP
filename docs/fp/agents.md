# OTTD-FP: правила параллельной работы агентов

Работа разбита на задачи в [backlog.md](backlog.md) (идентификаторы вида
`G1`, `R3`) и на GitHub issues с меткой `fp`, когда Issues в репозитории
включены; граф зависимостей — в бэклоге и в эпике. Каждая задача
самодостаточна: цель, контекст, где работать, что проверить. Этот
документ — общие правила для всех.

## Перед началом

1. Прочитать [architecture.md](architecture.md) (как минимум разделы,
   на которые ссылается issue), [README.md](README.md) и issue целиком,
   включая «Зависимости»: если блокирующее issue не закрыто, работать
   только над тем, что от него не зависит, или взять другое.
2. Базовая ветка — `master`.
3. Своя ветка на каждую задачу: `fp/<номер issue или ID>-<кратко>`,
   например `fp/12-walker` или `fp/r2-walker`. В PR указать
   `Closes #<номер>` (если есть issue) и ID задачи из бэклога.

## Границы и конфликты

- В разделе «Где работать» каждое issue перечисляет каталоги, которыми
  оно владеет. В чужие модули — только минимальные правки интерфейсов,
  отдельным коммитом с пояснением.
- Общие точки, которые трогают многие: `src/cab_view_3d.h` (камера,
  интерьер, поверхность для пешехода), класс `Renderer` в
  `src/cab_view_3d.cpp`, `src/cab_view_ride.*`. Правки в них — маленькие и
  аддитивные: новые поля и методы вместо переделки существующих. Так
  параллельные PR сливаются без боли.
- `src/cab_view_3d.cpp` большой; новые части рендерера (например, огни,
  контактная сеть) — отдельными методами `Renderer` рядом с похожими, а
  крупные новые подсистемы — в собственных файлах `src/cab_view_*.cpp` или
  `src/first_person_*.cpp`.
- Имена файлов — уникальные во всём проекте: этого требует CMake OpenTTD.

## Ядро OpenTTD

- Изменения ядра — как можно меньше и по одной строке: вызов функции из
  `first_person_gui.h` или `vehicle_gui.h` (как `FirstPersonVehicleGone()`
  в `Vehicle::PreDestructor` или закрытие окна кабины рядом с окном
  транспорта).
- Если нужно больше строки (как `CollectTileGroundSprites()` в
  `viewport.cpp`, где данные `static`), — это отдельная функция рядом с
  тем, чем она пользуется, и абзац в PR о том, почему иначе нельзя.
- Не менять формат сохранений и сетевой протокол без отдельного issue
  (см. architecture.md, §5.5 и §15).

## Правила кода

- Стиль — [CODINGSTYLE.md](../../CODINGSTYLE.md) OpenTTD: табы, `this->`,
  doxygen-комментарии у всего публичного, без функций из `safeguards.h`.
- Код, который выполняется внутри симуляции (команды, тяга и т. п.), —
  без float и без недетерминированных источников (architecture.md, §5.4).
- Потоки: окна (`OnGameTick`, `OnRealtimeTick`, `DrawWidget`) и с ними
  весь 3D-вид работают под блокировкой состояния игры; заливка кадра в
  потоках (`Renderer::Rasterise`) не трогает ни игру, ни кэш спрайтов.
  Кэш спрайтов и NewGRF-колбэки — только под блокировкой.
- Строки интерфейса — в `src/lang/english.txt` и `src/lang/russian.txt`.

## Проверка перед PR

1. Сборка без предупреждений в своих файлах:
   `cmake .. && make -j$(nproc) openttd openttd_test`.
2. Тесты: `./openttd_test` — все, включая новые тесты своего модуля
   (`src/tests/`).
3. Живой тест без видеокарты (3D-вид рисует процессор, нужен только Xvfb):
   `cab_view_dev/fp_live_test.sh <путь к openttd> <каталог> [шаги...]`.
   Скрипт запускает игру с тестовым ИИ, выполняет шаги и сохраняет
   скриншоты и вывод консоли (README, «Сборка и тесты»). Скриншоты,
   показывающие результат issue, приложить к PR.
4. Если в issue есть «Критерии приёмки», в PR отметить каждый.

## Определение готовности

- Критерии приёмки issue выполнены и показаны (тест, скриншот, вывод).
- Документация обновлена: README (что появилось, как пользоваться) и,
  если решение отличается от architecture.md, — сам architecture.md.
- Сохранения и сетевой протокол не изменены (или изменены по отдельному
  issue).
