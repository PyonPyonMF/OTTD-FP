# OTTD-FP: правила параллельной работы агентов

Работа разбита на GitHub issues с меткой `fp`; общий план и граф
зависимостей — в эпике. Каждое issue самодостаточно: цель, контекст, где
работать, что проверить. Этот документ — общие правила для всех.

## Перед началом

1. Прочитать [architecture.md](architecture.md) (как минимум разделы,
   на которые ссылается issue), [README.md](README.md) и issue целиком,
   включая «Зависимости»: если блокирующее issue не закрыто, работать
   только над тем, что от него не зависит, или взять другое.
2. Базовая ветка — `master`. Пока M0 не слит в `master`, база —
   `ccr-72500c40-0ww1lb`.
3. Своя ветка на каждое issue: `fp/<номер>-<кратко>`, например
   `fp/12-walker`. В PR указать `Closes #<номер>`.

## Границы и конфликты

- В разделе «Где работать» каждое issue перечисляет каталоги, которыми
  оно владеет. В чужие модули — только минимальные правки интерфейсов,
  отдельным коммитом с пояснением.
- Общие точки, которые трогают многие: `src/fp/fp_hooks.h`,
  `src/fp/runtime/fp_runtime.*`, `src/fp/render/fp_renderer.*`,
  `src/fp/sim/fp_snapshot.h`. Правки в них — маленькие и аддитивные:
  новые поля и методы вместо переделки существующих. Так параллельные
  PR сливаются без боли.
- Новые подсистемы — в собственных файлах и каталогах (например,
  `src/fp/sprites/`), а рендерер только подключает их.
- Все файлы режима — с префиксом `fp_`: CMake OpenTTD требует уникальных
  имён файлов во всём проекте.

## Ядро OpenTTD

- Изменения ядра — только хуки по образцу из README: одна строка с
  пометкой `/* FP hook */`, функция объявлена в `src/fp/fp_hooks.h` и
  без `WITH_FP` становится пустой inline-функцией.
- Если нужно больше строки (например, захват спрайтов в `viewport.cpp`,
  где данные `static`), — это отдельная функция в конце файла ядра,
  обёрнутая в `#ifdef WITH_FP`, и абзац в PR о том, почему иначе нельзя.
- Не менять формат сохранений и сетевой протокол без отдельного issue
  (см. architecture.md, §5.5 и §15).

## Правила кода

- Стиль — [CODINGSTYLE.md](../../CODINGSTYLE.md) OpenTTD: табы, `this->`,
  doxygen-комментарии у всего публичного, без функций из `safeguards.h`.
- Код, который выполняется внутри симуляции (команды, тяга и т. п.), —
  без float и без недетерминированных источников (architecture.md, §5.4).
- Потоки: симуляционные хуки и `Runtime::Update` выполняются под
  блокировкой состояния игры, `Renderer::Paint` — без неё и не трогает
  симуляцию (README, «Потоки»). Кэш спрайтов и NewGRF-колбэки — только
  под блокировкой.
- Строки интерфейса — в `src/lang/english.txt` и `src/lang/russian.txt`.

## Проверка перед PR

1. Сборка без предупреждений в `src/fp`:
   `cmake .. && make -j$(nproc) openttd openttd_test`.
2. Тесты: `./openttd_test` — все, включая новые тесты своего модуля
   (`src/fp/tests/`).
3. Живой тест без видеокарты: отдельный каталог сборки с
   `-DOPTION_FP_SOFTWARE_GL=ON`, затем
   `src/fp/tools/fp_live_test.sh <путь к openttd> <каталог> [команды консоли...]`.
   Скрипт открывает вид на заставке, двигает камеру и сохраняет
   скриншоты и вывод `fp status`. Скриншоты, показывающие результат
   issue, приложить к PR.
4. Если в issue есть «Критерии приёмки», в PR отметить каждый.

## Определение готовности

- Критерии приёмки issue выполнены и показаны (тест, скриншот, вывод).
- Документация обновлена: README (что появилось, как пользоваться) и,
  если решение отличается от architecture.md, — сам architecture.md.
- Без `OPTION_FP` проект собирается как ванильный.
